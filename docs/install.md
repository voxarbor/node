# Встановлення та обслуговування вузла

Для тих, хто ставить VoxArbor Node на свій комп'ютер. Технічний контракт (шляхи, поля `/capabilities`) описано
англійською в [gateway.md](gateway.md).

## Що потрібно

- Docker із compose v2 (Linux, або Windows/macOS із Docker Desktop чи WSL2).
- ~25 ГБ вільного диска (з відеокартою ~35 ГБ), бажано 16 ГБ RAM і 4+ ядра процесора.
- Для відеокарти: NVIDIA з драйвером для CUDA 12.8+ і nvidia-container-toolkit. Перевірка:
  `docker run --rm --gpus all ubuntu:24.04 nvidia-smi`.

## Встановлення одним скриптом (install.sh)

Скрипт `install.sh` лежить у цьому репозиторії й додається до кожного релізу разом із `SHA256SUMS`. Тож перед
запуском можна прочитати, що він робить, і звірити, що файл не підмінено.

**Найпростіше.** На сайті координатора в розділі «Мої вузли» є готова команда з вашим кодом приєднання.

**Із перевіркою (рекомендовано):**
```
curl -fsSLO https://github.com/voxarbor/node/releases/latest/download/install.sh
curl -fsSLO https://github.com/voxarbor/node/releases/latest/download/SHA256SUMS
sha256sum --ignore-missing -c SHA256SUMS          # має бути: install.sh: OK
less install.sh                                    # за бажанням: прочитати
sh install.sh --coordinator https://<координатор> --join <код>
```
`SHA256SUMS` ще й підписано (cosign keyless, GitHub Actions цього репозиторію). Звірити підпис можна так:
`cosign verify-blob SHA256SUMS --bundle SHA256SUMS.sigstore.json --certificate-oidc-issuer
https://token.actions.githubusercontent.com --certificate-identity
https://github.com/voxarbor/node/.github/workflows/release.yml@refs/tags/<тег>` (файл бандла лежить у тому самому релізі).

### Параметри

| параметр | що робить |
|---|---|
| `--coordinator URL` | адреса координатора (`https://…`), обов'язково |
| `--join CODE` | одноразовий код приєднання із сайту координатора, обов'язково |
| `--name NAME` | назва вузла на сайті (типово: ім'я комп'ютера) |
| `--services LIST` | важкі сервіси через кому: `tts`, `stt`, `diarize` (хоча б один) і за бажанням `fetch`. Типово `tts,stt,diarize`. Переклад і службові сервіси (шлюз, node-info, конектор, оновлювач) працюють завжди. `fetch` (завантаження з YouTube з IP цього ПК) вимкнено, доки його не вказати |
| `--gpu auto\|off` | `auto` (типово): відеокарта NVIDIA, якщо Docker її бачить; `off`: лише процесор |
| `--mode normal\|gentle` | `gentle` — економний режим: одна задача за раз і половина потоків |
| `--dry-run` | лише перевірити параметри й комп'ютер, нічого не змінюючи |
| `--uninstall [--yes]` | зупинити й повністю видалити вузол: контейнери, томи з моделями, образи вузла й теку |
| `--help` | довідка |

Змінні середовища: `GATEWAY_PORT` (8790), `NODE_DIR` (тека вузла, типово `~/voxarbor-node`; наявне встановлення в
`~/voice-core-node` скрипт знаходить сам і не переносить), `NODE_RELEASE` (конкретний реліз `vX.Y.Z`, типово
найновіший).

### Що робить скрипт, крок за кроком

1. **Перевіряє параметри.** Код приєднання дозволено лише з літер, цифр, `-` і `_`.
2. **Docker.** Якщо його немає: на Ubuntu й Debian ставить з офіційного apt-репозиторію download.docker.com,
   спершу перевіривши відбиток GPG-ключа Docker (`9DC8 5822 9FC7 DD38 854A E2D8 8D81 803C 0EBF CD88`). На інших
   системах зупиняється з посиланням на офіційну інструкцію. Сторонніх скриптів через `curl | sh` не запускає.
3. **Відеокарта.** Якщо `nvidia-smi` бачить NVIDIA і Docker запускає `--gpus all`, вмикає `compose.gpu.yaml`.
4. **Підпис і файли.** Завантажує з релізу GitHub `SHA256SUMS` і `manifest.json` та перевіряє їхні підписи
   cosign (образ cosign закріплено за digest). Підписувачем має бути workflow релізів цього репозиторію на цьому
   тезі. Потім завантажує `compose.yaml`, `Caddyfile`, `prune.sh`, `env.example` (і `compose.gpu.yaml` для
   відеокарти) і звіряє кожен із `SHA256SUMS`. Якщо щось не збігається, скрипт зупиняється.
5. **`.env`.** Записує адресу координатора, код, назву, версію релізу (`VOXARBOR_NODE_TAG`), випадковий локальний токен
   шлюзу (не залишає цей комп'ютер), потоки відповідно до ядер, обрані сервіси й режим. Шлюз слухає лише
   `127.0.0.1`: вузол сам підключається назовні, відкривати порти не треба. Права на `.env` — 600.
6. **Невибрані сервіси** вимикає в `compose.override.yaml`, тож їхні образи навіть не завантажуються.
7. **Образи.** Кожен образ (наші `ghcr.io/voxarbor/node-*` і закріплені сторонні: caddy, speaches) завантажується
   за digest із підписаного маніфесту, вхід не потрібен. Моделі перекладу копіюються в том один раз.
8. **Запуск** `docker compose up -d`, прибирання старих образів вузла (`prune.sh`). Потім скрипт чекає, доки шлюз
   відповість і конектор підключиться до координатора. Після підключення одноразовий код приєднання видаляється з
   `.env` (у вузла вже власний токен у томі `connector-state`).

Далі вузол оновлюється сам (див. «Автоматичне оновлення» і [security.md](security.md)).

## Встановлення вручну, без скрипта

На вузлі потрібні лише файли `compose.yaml`, `compose.gpu.yaml` (для відеокарти), `Caddyfile`, `prune.sh` і
`.env.example`, доступ до репозиторію не потрібен.

```
cp .env.example .env
sed -i "s/^NODE_TOKEN=.*/NODE_TOKEN=$(openssl rand -hex 32)/" .env
docker compose pull
docker compose --profile init run --rm init-opus     # один раз: моделі перекладу в том (~3,7 ГБ)
docker compose up -d
```

Перевірка: `curl -H "Authorization: Bearer <NODE_TOKEN>" http://127.0.0.1:8790/capabilities`. Усі сервіси мають
бути `"healthy": true`.

## Підключення до координатора

Вузол сам підключається до координатора через WebSocket, відкривати порт не треба. У `.env`:
```
COORDINATOR_URL=https://<адреса координатора>
NODE_JOIN_CODE=<код від координатора>
NODE_NAME=<назва вузла>
```
Після першого запуску код використано, і його можна видалити з `.env`. Вузол зберігає свій ідентифікатор і токен
у томі `connector-state`. Протокол описано в [connect.md](connect.md).

## Відеокарта NVIDIA

Додайте в `.env`:
```
COMPOSE_FILE=compose.yaml:compose.gpu.yaml
```
Тоді розпізнавання мовлення, озвучення й розпізнавання мовців (pyannote) працюють на відеокарті, а переклад лишається
на процесорі. Без відеокарти мовців розмічає легша модель sherpa-onnx на процесорі.

Якщо відеокарт кілька, вузлу можна дати лише частину: `NODE_GPUS=0` (перша) або `NODE_GPUS=0,1` у `.env`, потім
`docker compose up -d`. Типово `all`.

## Економний режим

Щоб вузол залишав більшу частину комп'ютера власникові, додайте в `.env`:
```
NODE_MODE=gentle
NODE_CPU_SHARES=128      # необов'язково: нижчий пріоритет процесора щодо інших контейнерів
```
і виконайте `docker compose up -d`. В економному режимі вузол бере одну задачу одночасно (також і для відеокарти), а
сервіси використовують половину потоків процесора. Задачі виконуються повільніше, зате комп'ютер лишається чуйним.
Координатор бачить режим у `/capabilities` як `node.mode`. Щоб повернутися до звичайного режиму, приберіть ці рядки
й знову виконайте `docker compose up -d`.

## Автоматичне оновлення (з 0.13.0)

Сервіс `updater` сам оновлює вузол до версії, яку призначає координатор (хвилями, з адмінки). Файли й образи він
бере лише з підписаного
релізу voxarbor/node на GitHub. Оновлюється лише тоді, коли вузол простоює, і сам відкочується до попередньої
версії, якщо після оновлення вузол не запрацював. Режим можна змінити в будь-який момент: впишіть потрібний рядок у `.env` у теці вузла й виконайте
`docker compose up -d`:
```
UPDATER_MODE=auto      # типово: оновлюватися самостійно
UPDATER_MODE=notify    # лише повідомляти, оновлюватися після кнопки «Оновити» на сайті
UPDATER_MODE=off       # не оновлюватися
```
Якщо власник поставив вузол на паузу на сайті, оновлювач нічого не завантажує й не змінює. Подробиці:
[security.md](security.md) (які права й чому) і [updater.md](updater.md) (англійською).

## Оновлення вручну (лише без оновлювача)

1. Візьміть нові `compose.yaml` і `compose.gpu.yaml` із тегу релізу та змініть `VOXARBOR_NODE_TAG` у `.env`.
2. Моделі перекладу копіюйте лише тоді, коли змінилася їхня версія (інакше кожне оновлення марно качатиме 3,7 ГБ):
   ```
   want=$(docker compose --profile init config --format json | python3 -c 'import json,sys;print(json.load(sys.stdin)["services"]["init-opus"]["environment"]["OPUS_MODELS_TAG"])')
   have=$(docker compose run --rm --no-deps --entrypoint cat translate /cache/opus-mt/.models-version 2>/dev/null)
   [ "$have" = "$want" ] || docker compose --profile init run --rm init-opus
   ```
3. `docker compose pull && docker compose up -d`
4. `./prune.sh` видаляє старі образи вузла.

Оновлюйте тоді, коли вузол не зайнятий: задачі, що виконуються, перериваються.

## Очищення

`./prune.sh` видаляє образи вузла, на які поточна конфігурація більше не посилається: старі теги
`ghcr.io/voxarbor/node-*` і образу розпізнавання мовлення, образ моделей перекладу після `init-opus`, а також
непозначені шари цього проєкту. Інше на комп'ютері не чіпає. `./prune.sh --dry-run` лише покаже, що буде видалено.

Образи мають спільні шари (ffmpeg і torch зберігаються один раз). Вузол із процесором займає ~11 ГБ образів, із
відеокартою ~27 ГБ.

## Завантаження з YouTube (необов'язково)

Для координатора, чию IP-адресу блокує YouTube: вузол завантажує дані, субтитри й аудіо зі своєї адреси. Увімкнення:
`COMPOSE_PROFILES=fetch` у `.env`. За потреби можна покласти `cookies.txt` у том `fetch-config` (`/config/cookies.txt`)
або задати `YTDLP_PROXY`.

**Не кладіть у `cookies.txt` cookies свого особистого акаунта Google/YouTube.** Через них вузол діятиме від
вашого імені, а координатор може попросити будь-яке відео. Якщо cookies справді потрібні, заведіть окремий
порожній акаунт лише для вузла.

## Скільки ресурсів бере вузол

Без задач моделі вивантажуються через 2 хвилини, і вузол бере ~0,3 % процесора й ~0,8 ГБ RAM. Під навантаженням
вузол на процесорі займає до ~7 ГБ RAM. Потоки й обмеження процесора задаються в `.env` (`STT_THREADS`,
`TTS_THREADS`, `TTS_CPUS` тощо, див. `.env.example`).

## Зупинити, вимкнути автозапуск, видалити

Усі команди виконуються в теці вузла (типово `~/voxarbor-node`):

| що | команда |
|---|---|
| зупинити зараз (і не запускати після перезавантаження) | `docker compose stop` |
| запустити знову | `docker compose start` |
| вимкнути лише автоматичне оновлення | `UPDATER_MODE=off` у `.env`, потім `docker compose up -d` |
| видалити вузол повністю (контейнери, томи з моделями, образи, теку) | `sh install.sh --uninstall` |

Зупинений через `docker compose stop` вузол не стартує сам після перезавантаження: контейнери мають політику
`unless-stopped`. Сам Docker лишається встановленим.
