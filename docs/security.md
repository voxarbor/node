# Безпека вузла

Що робить VoxArbor Node на вашому комп'ютері, які права має і як це перевірити. Вузол і інсталятор відкриті
(цей репозиторій). Координатор VoxArbor (сайт, розподіл задач) — закритий, але вузол не дає йому нічого, крім
описаного нижче.

## Що бачить координатор і де ставити вузол

Вузол виконує задачі координатора, тому **координатор бачить усе, що надсилає вузлу на обробку, і результати:** аудіо
для розпізнавання, тексти для перекладу й озвучення, згенерований звук, а з `fetch` — які відео з YouTube
завантажено. Інших даних вашого комп'ютера (файлів, програм, мережі) він не бачить, але вирішуйте, кому довіряєте
таку роботу.

**Рекомендуємо** ставити вузол на окремий ПК, віртуальну машину або окремий дистрибутив WSL, де немає важливих
документів, паролів чи ключів. Вузол працює в контейнерах, але оновлювач має доступ до Docker (див. нижче), тож
найпростіший захист — машина, на якій нема чого берегти.

## Мережа

- Вузол сам підключається до координатора одним WebSocket-з'єднанням (TLS). Відкривати порти на роутері чи комп'ютері
  не треба: шлюз вузла слухає лише `127.0.0.1`.
- Через це з'єднання координатор може надсилати лише запити до голосових сервісів вузла: розпізнавання, озвучення,
  переклад, розпізнавання мовців і, якщо ви ввімкнули `fetch`, завантаження з YouTube. Доступу до файлів, команд чи
  інших програм комп'ютера в нього немає. Протокол: [connect.md](connect.md).
- Локальний токен шлюзу (`NODE_TOKEN` у `.env`) не залишає комп'ютер. Координатор видає вузлу власний токен під час
  приєднання (зберігається в томі `connector-state`).

## Які дані про ваш комп'ютер бачить координатор

Вузол повідомляє координатору лише загальні характеристики, потрібні для розподілу задач і порівняння швидкості
(`/capabilities`, [gateway.md](gateway.md)). Повний перелік того, що стосується вашого комп'ютера:

| поле | приклад | навіщо |
|---|---|---|
| `node.cpu_model` | Intel(R) Core(TM) i7-4800MQ | модель процесора для бенчмарків |
| `node.cpu_threads`, `node.cpu_cores` | 8 | скільки потоків бачить Linux |
| `node.ram_total_gb`, `node.ram_available_gb` | 26.4, 23.9 | чи вистачить пам'яті на моделі |
| `node.load_avg` | [0.4, 0.4, 0.5] | наскільки зайнятий процесор зараз |
| `node.os` | Ubuntu 24.04 LTS · WSL2 | назва системи (без версії ядра) |
| `node.gpu`, `node.gpu_vendor`, `node.gpu_name` | true, nvidia, NVIDIA GeForce RTX 5070 Ti | яка відеокарта (у WSL без NVIDIA — `unknown`) |
| `node.vram_gb`, `node.vram_used_gb`, `node.gpu_util_pct` | 12.0, 0.5, 3 | пам'ять і завантаження відеокарти (NVIDIA) |
| `node.mode` | normal / gentle | режим вузла |
| `services.*.device`, `model`, `model_revision`, `engine`, `loaded` | cpu, Whisper turbo… | які моделі працюють і де |
| `services.*.perf` | `{"per_second": 2.4, "jobs": 12}` | швидкість за останню годину реальної роботи: секунд аудіо за секунду (розпізнавання, озвучення), речень за секунду (переклад) |
| версії вузла й сервісів, `updater.*` | v0.14.3 | стан оновлень |
| `NODE_NAME` (при приєднанні) | назва, яку ви дали | як вузол називається на сайті (типово ім'я ПК, можна змінити через `--name`) |

Вузол **не** передає: серійних номерів, MAC-адрес, UUID дисків чи плат, імені користувача, шляхів у ваших теках,
списку процесів чи програм, IP-адрес вашої локальної мережі. Через своє з'єднання координатор бачить лише
публічну IP-адресу, з якої вузол підключається (як будь-який сайт). Назву ОС вузол бере з `/etc/os-release` хоста:
цей файл підключено до сервісу node-info лише для читання.

## Оновлювач

Сервіс `updater` оновлює вузол до версії, яку призначає координатор, і відкочує невдале оновлення.

**Які права й чому.** Щоб замінити контейнери вузла, оновлювачу потрібен доступ до Docker (`/var/run/docker.sock`).
Це широкі права: через Docker можна керувати будь-якими контейнерами на цьому комп'ютері. Тому цей доступ має лише
оновлювач, і жоден інший сервіс вузла. Оновлювач не має відкритих портів і не з'єднується з координатором. Від
координатора через конектор він отримує лише назву бажаної версії (`vX.Y.Z`), режим і прапорці «зараз»/«пауза».
Адрес, файлів, образів чи команд координатор передати не може.

**Чому не docker-socket-proxy.** Ми розглядали проксі до Docker API з обмеженим набором дозволів. Але щоб
оновлювати вузол, оновлювачу все одно потрібні створення й видалення контейнерів, томів і мереж, завантаження образів
і запуск короткочасних контейнерів. Такий набір дозволів через проксі майже рівний повному доступу, тож він дав би
лише видимість захисту. Натомість ми обмежуємо, **що** оновлювач робить: він приймає ззовні лише номер версії, а все
інше бере з підписаного релізу (нижче). Якщо такий рівень довіри не підходить, вимкніть оновлювач
(`UPDATER_MODE=off`) і оновлюйте вручну.

**Як перевіряється реліз.** Перед оновленням оновлювач:
1. Завантажує з GitHub-релізу voxarbor/node файл `manifest.json` і його підпис `manifest.json.sigstore.json`.
2. Перевіряє підпис (cosign keyless, Sigstore). Підписувачем має бути саме workflow
   `.github/workflows/release.yml` цього репозиторію на цьому тезі. Без дійсного підпису оновлення не відбувається:
   запасного шляху немає. Корінь довіри Sigstore вбудовано в образ оновлювача (оновлюється з кожним його релізом), тож
   перевірка працює й тоді, коли сервери Sigstore недоступні.
3. Звіряє sha256 кожного файлу вузла (`compose.yaml`, `compose.gpu.yaml`, `Caddyfile`, `prune.sh`) з маніфестом.
4. Завантажує образи лише за digest із маніфесту і лише з дозволених репозиторіїв: `ghcr.io/voxarbor/node-*`,
   `ghcr.io/speaches-ai/speaches` і `caddy`.
5. Діє лише у власному compose-проєкті вузла. Перехід на старішу версію заборонено (хіба що
   `UPDATER_ALLOW_DOWNGRADE=1` у `.env`).

**Як вимкнути або обмежити.** У `.env`, потім `docker compose up -d`:
```
UPDATER_MODE=auto     # типово: оновлюватися самостійно, хвилями з адмінки
UPDATER_MODE=notify   # лише повідомляти; оновлюватися лише після кнопки «Оновити» на сайті
UPDATER_MODE=off      # не оновлюватися взагалі (оновлення вручну: install.md)
```
Повністю зупинити вузол: `docker compose stop` у його теці. Видалити: `sh install.sh --uninstall`
([install.md](install.md#зупинити-вимкнути-автозапуск-видалити)).
Налаштування в `.env` завжди сильніше за налаштування із сайту: з двох режимів діє суворіший. Пауза вузла на сайті
зупиняє й оновлення, і завантаження.

Детально (англійською): [updater.md](updater.md).

## Інсталятор

`install.sh` відкритий, і до кожного релізу додаються `SHA256SUMS` з підписом. Як звірити файл перед запуском:
[install.md](install.md#встановлення-одним-скриптом-installsh). Скрипт:
- ставить Docker лише з офіційного apt-репозиторію download.docker.com, спершу звіривши відбиток GPG-ключа (Ubuntu,
  Debian). На інших системах зупиняється з посиланням на інструкцію Docker;
- перевіряє cosign-підписи `SHA256SUMS` і `manifest.json` релізу (образ cosign закріплено за digest);
- завантажує файли вузла й звіряє їх із `SHA256SUMS`;
- завантажує кожен образ, і наш, і сторонній (caddy, speaches), лише за digest із підписаного маніфесту;
- після підключення видаляє з `.env` одноразовий код приєднання;
- шлюз слухає лише `127.0.0.1`, його `/health` нічого не розповідає про вузол.

`cookies.txt` для `fetch`: не кладіть туди cookies особистого акаунта ([install.md](install.md)).
